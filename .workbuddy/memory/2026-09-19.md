## 决定性发现（最新日志 + Python 交叉验证）

**Python 直接跑同一 ONNX 模型（CPU ORT）与 Unity（CUDA）输出完全一致**：skinMax=18.8964 分毫不差，前 20 个值 [0.208, 4.986, 9.737...] 完全一致。**证明 C# 绑定和模型本身都没有问题**。

- Python 实验：静音 skinRMS=0.108，正弦1.0 skinRMS=0.102，差异仅 1.065（skinMax 5.6%）

- ~93% 输出能量与音频无关，BVLS 把巨大噪声地板反解成权重 → "挤眉弄眼+和语音无关"

**常量噪声地板**：`constantNoise=true` + `noiseSeed=1234` → 每次推理噪声完全相同。静息脸标定可精确抵消噪声地板。

## 诊断「嘴歪眼斜」根因（对照官方 SDK 源码）

完整抓取了 NVIDIA/Audio2Face-3D-SDK 源码（animator_cuda.cu / blendshape_solver.cpp / blendshape_solver_base.cpp），逐行核对结论：**整条数学链路（求解器 ATA、正则项、scaleFactor、multipliers/offsets、active poses 映射、AnimatorSkin Step1/Step2 符号约定）全部与官方一致，无移植错误**。

### 根因 1：JSON 配置数组顺序不匹配 npz（真正凶手，最新发现）

bs_skin_config_Mark.json 里的数组（bsSolveActivePoses、bsSolveSymmetryPoses、bsWeightMultipliers、bsWeightOffsets）是**按 ARKit 52 标准顺序**排列的，而 bs_skin_Mark.npz 的 poseNames 是**按面部扫描顺序**排列的。两者不是 1:1 对应关系，实测 16/52 个 pose 的 active 标志错位。

**错位的直接后果**：「嘴歪眼斜」。求解器认为 jawLeft/mouthLeft 不活跃（实际读到的是 eyeLookIn/eyeLookOut 的 active=0），于是下巴左移和嘴角左移的能量被错误分配到 jawOpen 等活跃 pose，导致口型看起来扭曲、左右不对称。

**修复**：BlendshapeSolver.Load 新增 `RemapJsonArrays(p)`，在 JSON 数组赋值给 _activePoses/_symmetryPoses/_multipliers/_offsets 之前，先把它们从 ARKit 顺序重映射到 npz 顺序。

### 根因 2：DriveGain=4 全局放大（之前的错误修复）

Audio2FaceBlendshapeTester.OnDriverFrame 里 `raw * 4` 再 Clamp01，把本应 10%~30% 的微妙口型无差别顶到 100%，左右脸微小不对称放大成歪脸。**修复**：DriveGain 默认 1，滑条范围 0.8~1.5。

### 根因 3：BaselineRescale 默认 true

静息脸标定的 `(w-b)/(1-b)` 重归一化，当基线 b 接近 1 时放大残差误差。**修复**：默认 false。

### 根因 4：CalibrateRestPoseOnStart 默认 true

官方不做静息脸标定。**修复**：默认 false。

## 修复汇总

- **BlendshapeSolver.cs**：新增 `RemapJsonArrays(p)` 方法，在 JSON 加载后、使用前将 ARKit 顺序数组重映射到 npz 顺序；新增 styling 覆盖表（skin jawL/R + mouthL/R active 0→1 作为 backup，但实际不需要因为 remap 后它们已经是 1）；BaselineRescale 默认 false。
- **Audio2FaceBlendshapeTester.cs**：DriveGain 默认 1，范围 0.8~1.5。
- **Audio2FaceDiffusionComponent.cs**：CalibrateRestPoseOnStart 默认 false。
- **Audio2FaceAnimatorConfig.cs**：叠加舌头 stylization 值。

## 音频链路诊断（20:30，重要）

**误判陷阱**：曾误以为"点击播放后 audioRMS 仍恒为 0 = 音频没进模型"。实际是**诊断日志 bug**：在 `Audio2FaceDiffusionModel.Run()` 里添加 `_lastAudioRms` 字段时误删了 `audioRms = (float)Math.Sqrt(sq/_window.Length);` 这行 sqrt 计算，导致 audioRMS 永远被初始化为 0。两轮日志（点播放 vs 不点播放）权重完全一致，恰恰证明**音频一直在正常流入**，只是诊断值算错。

**已修复**：恢复 sqrt 计算，audioRMS 现在能正确反映输入音频强度。

**标定验证通过**：`[A2F权重]` 日志显示标定后静音 skin合计从 1.093 → 0.007（噪声地板抵消 99.4%），有音频时 skin合计上升到 ~0.23，jawOpen 从 0 → 0.021。基线减法机制工作正常。

**剩余问题**：jawOpen 绝对值极小（~0.02，满程 2%），即使有音频。这是模型本身对音频响应弱的固有特性（Python 实验已证：静音→满幅正弦差异仅 5.6%），不是管线 bug。口型幅度需靠 stylization 增益放大。

**诊断日志已精简**：删除了 pred[0..19]/分布/采样等刷屏日志（已完成使命），保留简洁的 audioRMS/predRMS/skinRMS/gruRMS 单行。

## 口型幅度小根因（21:00 最终定位）

**Python 决定性实验推翻「模型对音频响应弱」的旧结论**——之前用正弦波测试误判了。用真实语音 Mark_neutral.wav 复现：
- 滑动窗口（正常流式）：jawOpen 投影 ±0.25 波动（模型完全正常）
- **冻结窗口**（反复推理同一窗口）：jawOpen 稳定 0.017，gruRMS 稳定 0.314

Unity 日志 #7+ 的 jawOpen=0.02、gruRMS=0.33 与冻结窗口**完全吻合**；#6 的 jawOpen=0.148 是窗口首次完整音频的正常响应。audioRMS 从 #6 起恒定 0.0642 = 窗口内容冻结的直接证据。

**根因**：`Audio2FaceDiffusionComponent.ProcessClipRoutine` 每帧 push 4096 样本，但推理 400ms 才消费 8000。4.9 秒音频在 ~0.33 秒内全部塞进容量 16000 的 ring → 覆盖 → 窗口冻结在最后 16000 样本 → 后续推理反复用同一窗口 → GRU 收敛 → 口型消失。

**旧背压 `PendingFrames > FramesPerInference` 是错的**：帧队列随推理增长，无法阻止音频 ring 被覆盖。

**修复**：`Audio2FaceDiffusionPipeline` 新增 `UnconsumedAudioSamples`（=_ringTotal-_consumedUntil）和 `RingCapacity` 属性；`ProcessClipRoutine` 背压改为 `while (UnconsumedAudioSamples >= RingCapacity) yield return null`，让 push 匹配消费速度，窗口持续滑动。

**附带诊断**：`[A2F窗口]`（Tick 触发时打印 ringTotal/consumed/ringHead/窗口前3样本）、`[A2F推流]`（push 进度 + 未消费样本数），前 12 次输出，验证修复后窗口是否滑动。

## 【推翻旧结论】RemapJsonArrays 是错的（21:20）

**修复窗口冻结后，口型幅度恢复正常（jawOpen 0.02→0.848 跟随音频波动），但暴露出新问题：嘴张得过大 + 眼睛上下抖动。**

**决定性证据（SDK 源码 + Python 逐位对照）**：
1. SDK `parse_helper.cpp:883` 读 JSON 的 `bsSolveActivePoses` 数组后**直接按 index 用，无任何 remap**；`SetBlendshapeConfig → SetActivePoses` 里 `activePoses[i]` 直接对应 npz `poseNames[i]`。
2. Python 逐位对照确认：**JSON 数组本身就是 npz 顺序**（索引0=eyeBlinkLeft=1, 1-4=eyeLook系列=0, 17=jawOpen=1... 全部吻合）。唯一差异：jawLeft/jawRight/mouthLeft/mouthRight 在 JSON 里=0，但官方 stylization yaml 里=1——恰好是 `SkinActiveOverrides` 已覆盖的四个。

**结论：之前加的 `RemapJsonArrays`（把 JSON 误当 ARKit 顺序重排到 npz 顺序）是错误的重排**，它把正确的顺序打乱，导致：eyeLook 系列被错误激活（眼睛上下抖动）、嘴部 pose 能量错位（嘴张得过大）。

**已修复**：删除 `RemapJsonArrays` 方法及调用，JSON 数组直接按 npz 顺序使用（`_activePoses = p.bsSolveActivePoses` 等）。

**教训**：之前"JSON 数组顺序 ≠ npz 顺序"的结论是错的，实际两者本来就一致。SDK 源码里没有 remap，就是最直接的证据。

## 【最终结论】口型幅度大是官方增益，非 bug（21:35）

用户仍反馈"嘴巴张开的幅度不对"。用 Python **完整复现 SDK 链路**（模型推理 + AnimatorSkin + BVLS，xorshift128 噪声 + Mark 官方增益）得到黄金序列：

- **jawOpen max = 0.986，mouthClose max = 1.0**（接近满幅）
- BVLS 自检通过：单 pose delta 还原 jawOpen=0.999、mouthClose=0.953；全零 delta 解出 0

**关键数据校准**（之前 check_scalefactor 误读）：
- bs_skin 的 neutral/pose 数组是 `(24002,3)` = 72006 分量 = 24002 顶点（不是 8000！之前 `len(neutral)//3` 对 2D 数组算错）
- scaleFactor=0.99（targetBBSize=53.19 vs templateBBSize=53.45，正常）
- neutral_skin(model_data) vs bs_neutral(bs_skin) 最大差 0.89（float/版本小差异，SDK 同设计：animator 用 neutral_skin、solver 减 bs_neutral，baseline 标定可抵消这个静态偏移）

**结论**：口型幅度大（Unity jawOpen 0.69）是**官方行为**——Mark 官方 stylization 增益 `lower_face_strength=1.4 × skin_strength=1.1 × input_strength=1.3 ≈ 2 倍`，本身就把模型原始 jawOpen（~0.24）放大到接近满幅。Unity C# 移植正确（求解器/animator/数组对齐/scaleFactor 全部与 SDK 一致），甚至因 baseline 标定比纯模型输出（0.98）还小。

**调节口型幅度（不是改 bug，是调参）**：
- 方案 A：`Audio2FaceDiffusionComponent.Strength`（默认 1.0，<1 缩小，如 0.6~0.7）
- 方案 B：`Audio2FaceDiffusionConfig.overrideSkinAnimator=true` + 手填 `skinAnimator`（lowerFaceStrength/skinStrength 调低）
- 方案 C：改 `Audio2FaceAnimatorConfig.OfficialStylization` 里 Mark 的 lower_face_strength(1.4→1.0)/skin_strength(1.1→1.0)

## 【最终方案】仿照 UE 套 weight_multipliers（22:10）

搜索确认 UE（ACE Unreal Plugin）的用法：**UE 不直接跑 SDK，而是连 Audio2Face-3D 微服务**，微服务在 stylization config 里对模型解出的 ARKit 权重套一层 `weight_multipliers`。这层正是 UE 口型不夸张的根因，而 `bs_skin_config_*.json` 的 `bsWeightMultipliers` 全是 1.0（SDK 库层不套）。

官方微服务 multiplier（docs.nvidia.com/ace 的 audio2face_ms，1.2/2.0 版一致）关键值：
- **mouthClose 1.0→0.3**（闭唇闭死根因）、**jawOpen 1.0→0.8**、jawForward 0.7、jawLeft/Right 0.2、mouthLeft/Right 0.2
- mouthStretchLeft/Right 1.0→0.05、cheekPuff 0.2、mouthFrown 0.5、mouthRollUpper 0.5、mouthShrugUpper 0.4
- 放大：mouthSmile 1.2、browDown 1.2、browInnerUp 1.3
- UE 官方还专门改 `mh_arkit_mapping_pose_A2F`（改了 BrowDownLeft/Right、BrowInnerUp、MouthClose、MouthRollLower 五个曲线）+ bypass 默认 MetaHuman 的 MouthClose 动画，与 multiplier 表配套

**Unity 仿照实现**：`BlendshapeSolver.SkinMultOverrides`（原为空字典）填入官方微服务 multiplier 表（按小驼峰 pose 名，如 `["mouthClose"]=0.3f`）。`ApplyMultOverrides` 在 Load 时按 `PoseNames[i]` 匹配覆盖，`SolveCore` 里 `w *= _multipliers[i]` 生效（在 baseline 减法前，等价于增量×multiplier，正确）。

**注意**：PoseNames 是 npz 里的小驼峰（`jawOpen`/`mouthClose`），字典 key 必须小驼峰（之前误写 PascalCase `JawOpen` 会匹配失败）。

**调优（22:20）**：日志确认 multiplier 生效（mouthClose 0.678→0.203 抿嘴解决，jawOpen 0.696→0.5565）。但用户反馈「讲话嘴张不开」——jawOpen 的 0.8 是 UE 给 MetaHuman 的（MetaHuman 张嘴 blendshape 幅度大），Sloth_Head2 这类非 MetaHuman 网格张嘴幅度本来就小，再压 0.8 反而太小。**修正：jawOpen 0.8→1.0（只压 mouthClose，不压张嘴）**。真正要压的只有 mouthClose（之前 0.678 抿嘴）。
