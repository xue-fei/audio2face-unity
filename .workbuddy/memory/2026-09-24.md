# 2026-09-24（第十五轮）CUDA 已生效 + 拆分计时：瓶颈不在 GPU，在 CPU 解算

## 用户问题
「当前使用的是gpu推理还是cpu推理，优化一下推理速度」→「每帧推理耗时多少？」

## 结论 1：GPU 已经生效
启动日志 `★ 推理后端=CUDA（device 0）`，`[A2F推理] … 后端=CUDA`。
（第十四轮移除 `onnxruntime-cpu` 包生效——之前是同名 onnxruntime.dll 冲突导致静默回退 CPU。）

## 结论 2：单次耗时拆分（从日志直接读出来的，不用改代码就能算）
WorkerLoop 的计时覆盖 `Run + SolveCenterFrames`，而 `SolveCenterFrames` 里
`if (!warmup)` 会**整段跳过 30 帧解算**（warmup = `_windowEnd < BufferLength`）。
所以日志里那两条快的就是纯 ONNX 时间：
```
[A2F推理] #1 单次=128ms   ← warmup，跳过解算，首次含 CUDA kernel/cudnn autotune
[A2F推理] #2 单次=62ms    ← warmup，跳过解算 ⇒ 纯 ONNX 推理 ≈62ms
[A2F推理] #3 单次=373ms   ← 正式帧，含 30 帧解算
#4~#20 稳定 353~380ms，尖峰 595/653ms
```
**拆分结果（每次推理 = 0.5s 音频 / 30 个动画帧）：**
| 段 | 每次 | 每动画帧 | 占比 |
|---|---|---|---|
| ONNX Run（CUDA） | ≈62ms | ≈2.1ms | 17% |
| 30 帧解算/动画（CPU） | ≈310ms | ≈10.3ms | **83%** |
| 合计 | ≈372ms | ≈12.4ms | 100% |

RTF：0.372s 计算 / 0.5s 音频 = **0.74**（能实时，余量 1.34×）；
尖峰 653ms 时 RTF=1.31 会掉队。GPU 侧 RTF 只有 0.124 → **GPU 还有 8 倍余量，完全不是瓶颈**。
队列从 60 涨到 159 也印证生产(80fps) > 消费(60fps)。

## 结论 3：CPU 解算的钱花在哪
`BlendshapeSolver.Solve → SolveCore()`：
1. `b = D^T·target`：k≈50 活跃 pose × _numPositions(≈6 万，24002 顶点×3 的 frontalMask 子集)
   = **300 万次 double 乘加**，C# 非 SIMD、还带 float→double 转换 → 单帧大头
2. `Bvls.Solve`（有界变量最小二乘，迭代）→ 有 `_prevWeights` 时间正则，**帧间串行依赖**
3. SkinAnimator.Animate（顶点重建）
→ 每帧合计 ≈10.3ms × 30 帧。

# 第十六轮：BVLS + animator 双优化（用户「1和2都要搞」）

## 改动 1：BVLS（原最大单项 117ms/次）
`Bvls.cs` 重写为 `BvlsWorkspace` 实例类（原 `Bvls` 静态类保留为薄封装 + ThreadStatic 池）：
- **工作区复用**：原实现每次 `ConstrainedMin` 都 `new` freeVars/aFree(n×p)/xFree/bFree…，
  一次 Solve 里被调用几十次、每帧还解两遍（cancelPairs）→ 十几 MB/30 帧的纯垃圾。全部预分配。
- **正规方程 + Cholesky 取代 Householder QR**：
  自由子问题 min|A[:,F]xF − bFree|² 的正规方程是 (AᵀA)_FF xF = (AᵀbFree)_F；
  A 对称 → AᵀA = A·A = **G 可缓存**（Load 后 A 不变），A·b 每次 Solve 算一次。
  于是每次 ConstrainedMin 只剩 rhs_F = (Ab)_F − G_{F,C}·x_C（O(p·n)）+ Cholesky(G_FF)（O(p³/6)），
  而 QR 是 O(2np²) 且还要把 A(:,F) 拷一份 n×p。n≈p≈43 时常数差 ~10×。
- 代价 cond(G)=cond(A)² → 全程 double；Cholesky 不收敛（`d <= maxDiag*1e-13`）自动回退 QR（`CholFail` 计数）。
- `BlendshapeSolver.UseBvlsNormalEquations` 静态开关可整体关掉对拍；
  `BvlsWorkspace.VerifyOnce` 首次 Solve 自动跑一遍 NE vs QR 对拍并打印最大权重偏差（日志 `[BVLS对拍]`）。
- 每个 solver 持有自己的 `_bvls` 实例（Load 里 new），避免字典查找 + 让 G 缓存长期有效。

## 改动 2：SkinAnimator（原 ~120ms/次）
`Audio2FaceSkinAnimator.cs`：
- **掩码视图（最大头）**：solver 只按 frontalMask 读 4262/24002 顶点，而插值状态是**逐分量独立**
  （l1[i] 只依赖 l1[i]/l2[i]）→ 可以只重建掩码顶点。新增 `SetMask(int[] 分量级掩码)` +
  `AnimateMasked(...)`（读按全量 3v+c、写按紧凑 3k+c），配套 `BlendshapeSolver.SolveMasked()`。
  faceMask 的 Y 归一化**必须沿用全量 neutral 的 minY/maxY**（否则 mask 值整体偏移）。
  工作量降到 1/5.6，数值上与全量路径逐位一致。
- **干掉插值第 0 层**：SDK Interpolator degree=2 的 dataArr[0] 只是 raw 缓冲，写完立刻读回来算 l1，
  从无跨帧价值 → 状态数组 3 层降到 2 层（`_loL1/_loL2/_upL1/_upL2`），每分量省 2 写 2 读。
- **内层 3 分量手动展开**：mask/强度每顶点只取一次，三条分量链独立（ILP 更好）。
- alpha = 1 − 0.5^(dt/smoothing) 按 (dt, smoothing) 缓存，省两次 Mathf.Pow/帧。
- 全量路径与掩码路径各自独立的状态数组，`Reset()` 清两套；`SkinVertices`（全量）保留给 Probe 用。

`Audio2FaceDiffusionPipeline.cs`：solver 建好后 `SetMask(_skinSolver.MaskPositions)`，
`_skinVerticesMasked = new float[SolvedPositionCount]`，`SolveSkinAt` 优先走快路径；
debugMode 打印 `skin animator 掩码视图已启用: 顶点 24002 → 4262（18%）`。

## 新发现（不在本轮范围内）：队列无限增长
`队列` 30→60→90→112→…→385（第 21 次），每次推理净增 ~18 帧，从不收敛。
根因：`ProcessClipRoutine` 阶段 3 每帧 push 4096 样本（=0.256s 音频）= **15 倍实时推流**，
唯一背压是 `UnconsumedAudioSamples >= RingCapacity(32000)`。推理线程因此永远有活干、
以 ~1.6× 实时速度把整段音频提前算完（22.6s 音频 → 最终堆积 ~1360 帧）。
短音频只是"提前算完"，长音频/麦克风实时输入会持续累积延迟。
修法：阶段 3 按**音频播放时钟**节流（`audioSource.time + lead > cursor/sampleRate` 才 push，lead≈0.5s），
而不是只靠 ring 容量背压。静默模式（PlayAudioWhileProcessing=false）用 realtimeSinceStartup 计时。

## 第三轮：4（推流背压）+ 2（BVLS 相对容差）

### 4. 推流背压（`Audio2FaceDiffusionComponent.ProcessClipRoutine` 阶段 3）
按播放时钟节流，不再只靠 ring 容量：
- 新增 config `maxPushAheadSec = 1.0f`（已推音频最多领先播放头多少秒）
- **关键坑**：预缓冲为了攒 prebufferFrames 帧必然已多推 ~2s 音频，直接用配置值会在开播瞬间干等、
  队列被抽干、脸僵住 → lead 取 `max(config, 开播那一刻的实际领先量)`，**只保证不增长，不回压**。
  实测开播时 cursor=32384 (=2.024s)，lead 被抬到 2.024s，之后 ahead 稳定在 2.02s。
- 节流后生产速率（30 帧/0.5s 音频）== 消费速率（60 帧/s），队列收敛不再涨
- 兜底：`isPlaying` 为 false（播完/暂停）立即放弃节流；另有 5s realtimeSinceStartup 超时 + LogWarning
- push 日志加了 `领先播放=Xs(限 Ys) 队列=N帧`，并把 `pushCount<12` 放宽为 `<12 || %120==0`

### 2. BVLS 相对容差（`Bvls.cs` + `BlendshapeSolver.cs`）
判据是 `max|g|`、g=A^T(Ax−b)，而 b=D^T·target 量级 1e3~1e5，SDK 的绝对 1e-10 永远达不到，
主循环只能靠「无变量想脱离边界」退出（实测 18.4 次迭代/帧）。
- 新增 `BvlsWorkspace.RelativeTolerance`（默认 1e-6）+ `BlendshapeSolver.BvlsRelativeTolerance`（同名静态开关）
- 阈值 = `max(绝对 tolerance, RelativeTolerance × 梯度量级)`；量级取 **x=0 处的 |A·b|**（A 对称 → A^T b = A·b），
  与热启动的 x 无关，是稳定参考量；O(n²) 一次，可忽略
- 停滞判据 `|Δoptimality| < 1e-6` 也跟着改成 `max(1e-6, 阈值×1e-3)`（原来对 1e3 量级形同虚设）
- `LastThreshold` 暴露给 `[解算耗时]` 日志（`KKT阈值=...`）
- **精度验证升级**：`SolveVerified` 从跑 2 遍变 3 遍，第 3 遍把阈值压到 0（绝不提前退出），
  日志第二行 `放宽容差(阈值=..., 相对=...) vs 收紧到 0：最大权重偏差=...`，>1e-3 打 ⚠

### 实测结果（第三轮跑完）
**4 成功**：队列 30→60→90→110→109→108→106→105→104→102→100→99→98→97→94…，
`[A2F同步] 队列` 稳定在 86~89。之前是 30→385 单调涨。领先播放锁在 2.02~2.28s
（每次 push 0.256s 造成的锯齿，符合预期）。`开播时已领先 2.02s，节流阈值抬到 2.02s`

**2 基本无效（我的假设错了）**：KKT阈值从 1e-10 变成 `3.2E+000 / 1.1E+001`
（说明梯度量级 ~1e7，量级判断没错），但迭代只从 18.4 → 17.4/16.7，
BVLS 耗时 1.037 → 1.049~1.063 ms/帧（噪声内，甚至略慢，多算了一次 O(n²) 的 GradientScale）。
**原因**：主循环的实际出口不是 `optimality < threshold`，而是 `VarToDetach` 返回 −1（KKT 真正满足）
或 `costNew > cost`。这个 active-set 算法一次迭代只放开**一个**边界变量，
43 维有界问题本身就要 ~17 次。阈值只影响尾巴，省得下 1 次。
tongue（k=16）3.5→2.4 次，稍有效。
→ **BVLS 的迭代次数是算法固有成本，不是容差问题**。要动得换算法或砍掉每帧第二次 Solve。

**性能净变化 ≈ 0**：后处理 129~130ms（与上轮 130 相同），单次 ~187ms，RTF 仍 ~0.37。
本轮拿到的是正确性（队列不再无限增长），不是速度。

## 实时性判据（RTF 0.37 已够用，别再压吞吐）
- 吞吐：187ms 算 0.5s 音频 → 2.67x 余量。**瓶颈天花板在目标机 CPU 不在 GPU**：后处理 129ms 是
  纯 CPU 单线程（BVLS 帧间串行，无法 Parallel.For），GTX1070 上的 RTF 不能外推；低端 U 系列
  CPU 可能 2~3 倍慢 → RTF 逼近 1。**判据要在目标机 + IL2CPP Build 上复测**（编辑器 Mono 下
  `Vector.IsHardwareAccelerated=false`，真机 Build 通常更快）。
- 抖动容限：队列 86~110 帧 = 1.4~1.8s 冗余，实测单次推理波动仅 ±10ms（56~66ms），
  冗余是需要的 100 倍。安全值其实 20~30 帧就够扛 2 倍耗时尖峰或 100ms GC。
- **关键澄清：队列深 ≠ 延迟高**。队头紧跟播放头（同步差 -17~-33ms 已验证），队列里堆的是
  「未来帧」，只提供抗抖动冗余 + 占内存，不进入端到端延迟。端到端首帧延迟 ≈ warmup 1.0s
  + 音频窗 0.5s + 计算 0.19s ≈ **1.4~1.7s，由模型结构决定，压 RTF 压不掉**。
- 结论：**别再为「降延迟」去压 prebufferFrames / maxPushAheadSec**。真要压队列是为了省内存，
  且改 `maxPushAheadSec` 单独不生效 —— `lead` 会被开播领先量顶住（`Mathf.Max`），
  开播领先由 `Config.prebufferFrames` 决定（pushTarget = warmup + prebuffer×266.67 样本）。
- 剩余优化收益都很小：cancelPairs 第二次 Solve ≈ 省 15ms/次（RTF 0.37→0.34）；
  D^T 上 Burst ≈ 省 36ms/次（RTF →0.30）。**优先级应转向**：目标机复测 + 修 `未消费` 为负
  （背压1 现在形同虚设，节流实际全靠背压2 的音频时钟；接麦克风实时输入时会出事）。
