## 两段数据的确切语义（写死，别再猜）

### jaw_size = 15 = **5 个下颌标记点的位移**（不是欧拉角/四元数）
`animator.cpp:579 AnimatorTeeth::ComputeJawTransform`：
```
jawPose.x = res.x * lowerTeethStrength
jawPose.y = res.y * lowerTeethStrength + lowerTeethHeightOffset
jawPose.z = res.z * lowerTeethStrength + lowerTeethDepthOffset
jawPose  += neutralJaw           // model_data npz 的 neutral_jaw (5,3)
jawTransform[16] = rigidXform(jawPose, neutralJaw, 5)
```
`math_utils.cpp rigidXform` = Kabsch：H = b_delta^T·a_delta（b=neutralJaw 源，a=jawPose 目标），
SVD → R = V·diag(1,1,det(V·U^T))·U^T，t = aMean − R·bMean，输出**列主序** 4x4（平移在 12/13/14）。
→ 牙齿挂在骨骼上，**只有这一步能让牙齿动**；光驱动 blendshape 嘴能张开但牙不动。

### eyes_size = 4 = 左右眼各 2 个旋转角（度）
`animator.cpp:797 AnimatorEyes::ComputeEyesRotation`：
```
right.x = rightEyeRotOffsetX + eyeballsStrength*res[0] + saccadeStrength*saccadeRot[2*i+0]
right.y = rightEyeRotOffsetY + eyeballsStrength*res[1] + saccadeStrength*saccadeRot[2*i+1]
left.x  = leftEyeRotOffsetX  + eyeballsStrength*res[2] + saccadeStrength*saccadeRot[2*i+0]
left.y  = leftEyeRotOffsetY  + eyeballsStrength*res[3] + saccadeStrength*saccadeRot[2*i+1]
z 恒为 0
```
`saccade_rot_matrix (5000,2)` 是预生成随机眼动，**按 30fps 推进**（SDK 注释明确）、seed 决定起点、到尾回绕。
这是「眼睛不死盯前方」的唯一来源。

# 2026-09-22（第八轮）离线跑 ONNX 拿真值：修 jaw 杠杆臂 bug + 幅度

## 方法（以后排查同类问题照这个来）
`onnxruntime` 在系统 Python 3.12（`C:\Users\XUEFEI\AppData\Local\Programs\Python\Python312\python.exe`）里有，
managed 3.13 没有 numpy。模型输入：
```
window[1,16000] identity[1,3] emotion[1,30,10] input_latents[2,2,1,256] noise[1,3,60,88831]
→ prediction[1,60,88831]
```
stride=8000，latents 每次把 output_latents 回灌。CPU 上一次约 0.5s（724MB 模型）。

## 实测结论（写死）
1. **prediction 的 skin 段是 delta（位移），不是绝对坐标**：中心帧 RMS 0.09~0.22、max 0.57~1.46。
   `neutral_skin` 才是绝对坐标（y∈[135,170]，rms 88.9）。→ `Audio2FaceSkinAnimator` 的处理是对的。
2. **Unity 日志里的 `predRMS=3.90 / skinRMS=6.12 / skinMax=18.9` 恒定不变不是 bug**：
   那段统计跑在 `_prediction` 的 **frame 0**（左截断帧，本来就该丢），而且 predRMS 覆盖全部 60 帧
   （左右截断帧数值很大）。中心帧才是有意义的，别拿这三个数判断模型有没有响应。
3. **jaw 段确实是位移，但量很小**：实测 y∈[−0.01,−0.88]、z∈[−0.2,+0.02]，Kabsch 角 **0.4°~4.1°**。
4. **Kabsch 的 t 是「绕 A2F 模型原点旋转」的杠杆臂，不能拿去驱动骨骼**：
   实测 t.z 最大 10.7，而真实下颌质心位移只有 −0.71（= 151.65×sin(4.03°) = 10.67，完全吻合）。
   之前 `JawBone.localRotation += localPosition += t` 是**重复计算**，会把下颌整个推出去。
   正确分解：真实平移 = `mean(delta)`（质心位移）；旋转用 angle+axis 绕骨骼轴。
5. **jawOpen 与其它 pose 几乎正交**：把 jawOpen 的位移用全部 52 个 pose 做线性分解，
   自身系数 1.000、其余全部 ~0.000 → **可以安全地单独放大 jawOpen**，不会像放大
   `lowerFaceStrength` 那样把闭唇通道一起放大重新饱和。
6. **与 jawOpen 反向共线的通道**（会抵消张嘴）：mouthShrugLower −0.901、mouthPressRight −0.617、
   mouthPressLeft −0.550、jawForward −0.378、cheekPuff −0.361。mouthClose 只有 +0.053（几乎正交，
   不是主犯）；mouthPucker −0.170、mouthFunnel −0.151（弱）。

# 2026-09-22（第九轮）两个真 bug：改默认值不生效 + 唇缝探针写错了

## BUG 1（重要，通用坑）：Unity 序列化会让「改代码默认值」完全不生效
现象：日志里 `overrideFaceStrength(lower=0.80,skin=1.00)`、`+lip=0.35`，
但代码里已经改成 `lowerFaceStrength=1.0f`、`jawOpenToLipOpen=0.5f`。
同一轮新增的 `jawOpenGain=1.5` 却生效了（jawOpen 峰值 0.40→0.60 = ×1.5，与 lower 仍是 0.8 自洽）。

结论（Unity 序列化语义）：
- **新增字段** → 之前没序列化过 → 用代码默认值 ✓
- **已存在字段** → 场景/预制体里存的是「该字段第一次出现时」的默认值，
  之后改代码默认值**永远不会生效**，Inspector 也显示旧值 ✗
- 磁盘上的 `Assets/Scenes/audio2face.unity` 里 Config 块是旧版本快照
  （只有 modelFolder/identity/…/debugMode，没有 lowerFaceStrength 等），
  但 Editor 内存里持有旧值 → **改 YAML 也没用**（除非重载场景）。

解法（已实现）：`Audio2FaceDiffusionConfig` 加 `[HideInInspector] configVersion` +
`Migrate()`，`Audio2FaceDiffusionComponent.Start()` 里先调一次并打日志。
**以后改这个类任何默认值，必须 `LatestConfigVersion` +1 并在 Migrate() 里写迁移。**

## BUG 2：唇缝探针单点 + 符号反了
旧实现挑 mouthClose 形变里 Δy 最小 / 最大的**单个**顶点当上唇/下唇，
然后 `aperture = Σ w·(Δlower − Δupper)`。
- 符号反了：正确应该是 `Δupper − Δlower`（唇缝 = 上唇Y − 下唇Y）。
  反了之后 mouthClose 恒为正、jawOpen 恒为负。
- 实测 `[0.0004 .. 0.0335]` 全为正 → 印证符号错误（闭唇帧都没出现负值）。
- 单点顶点很可能落在嘴角 / 根本不在唇上 → 测出来的数没有意义。

新实现（已改）：区域加权 + 符号自洽 + 量纲归一化
1. mouthClose Δy 的 |Δ| > 25% 峰值的顶点 = 唇部区域；按方向分组
   `Δy<0 → 上唇 s=+1`，`Δy>0 → 下唇 s=−1`
2. 每个 pose 的系数 `_lipCoeff[i] = mean_over_region(s_v · Δy_v)`。
   构造上保证 **mouthClose 为负（闭）、jawOpen 为正（开）**
3. `_lipRefHeight = mesh.bounds.size.y`，结果统一报 **% 网格高**
   （说话时 max 应到 2~6%，<1% 就是看不出张嘴）
4. 启动时打：区域大小（上唇 n / 下唇 m）、包围盒高、jawOpen 形状最大顶点位移、
   9 个关键通道满权重时的唇缝变化 %。**jawOpen 系数≈0 会直接告警**
   （说明该形状只带下颌不带嘴唇 = 「下巴动了但嘴没张开」）
5. 每 60 帧打区间 + **最大张口那一帧的成因分解**（jawOpen / 唇分开组 / 闭唇组 / 其它）

## 其它
- `JawBone == null` 时启动告警（日志里 `下颌下降峰值≈0.000` 说明用户没绑骨骼）
- Sloth_Head2 舌头通道 0/16，牙齿若是独立网格/挂骨骼则 blendshape 带不动

# 2026-09-22（第十轮）探针 v2 实测是坏的 + 迁移 v1 也漏了 → 重写 v3 并加 BakeMesh 自检

## 从用户贴的日志里读出来的三件事

1. **迁移 v1 没把 jawOpenToLipOpen 清掉**：日志有 `配置已升级到 v1`，但 `[A2F嘴部]` 仍是
   `+lip=0.35`。原因：v1 写的是「只在旧值非法时才重置」（`if (v <= 0f) v = 0.5f`），
   而 0.35 是完全合法的值 → 被原样保留。**结论：迁移必须按版本号无条件覆盖，
   不能用「值是否合法」当判据。** 已加 `configVersion < 2` 分支整体覆盖口型开合那一组。

2. **唇缝探针 v2 测出来的数全是反的，不能读**：
   `[A2F唇缝] 探针已建：唇部区域 963 个顶点（上唇 963 / 下唇 0）`
   → mouthClose 在 Sloth_Head2 上的显著顶点 **100% 是 Δy<0**，分组直接退化成一坨，
   sgn 全 +1。于是 jawOpen=−9.42% 与 mouthClose=−9.64% 同号，张开/闭合分不出来。
   → `区间 [-9.43% .. -0.34%]` **不能**读成「没张开」；`最大张口那一帧`实际选的是
   开放量最小的帧。旧区间很可能是「下颌整体往下掉 9.4% 网格高、嘴唇仍合着」——
   正好就是用户说的「下巴向下移动了但嘴巴没张开」。

3. **网格侧的结构性限制（代码改不了，得改资产）**：没填 Jaw Bone（牙齿不动）、
   0/16 舌头形状（舌头不可能动）、只绑了 1 张网格、eyeSquintRight/tongueOut 缺失。

## 探针 v3（已实现，别再退回 v1/v2）
- 定位器换成 ARKit 语义最明确的两个形状：
  上唇组 = `mouthUpperUpLeft` 形变最集中的顶点；下唇组 = `mouthLowerDownLeft` 形变最集中的顶点
  （`PickStrongestVertices`：按 |Δ| 降序取前 60，位移掉到峰值 20% 以下就停）
- 张开方向 `_lipNormal` = 静息「上唇质心 − 下唇质心」的单位向量（**轴无关**，
  Sloth_Head2 是 Maya 导入，轴向不一定 Y-up）
- 系数 `_lipCoeff[i] = Dot(mean(上唇Δ) − mean(下唇Δ), _lipNormal)`
  → 下唇下降 / 上唇上抬都给正值，闭唇给负值，符号由构造保证
- `MeasureMouthAperture` 追加该帧 jawOpen 权重本身，防止索引错位被误读成幅度问题

## 新增 `[A2F自检]`（启动跑一次，最关键的一条日志）

# 2026-09-22（第十一轮）探针 v3 死在 mesh.vertices；[A2F自检] 已定案 → 改 v4 实测 + 加 [A2F实测]

## 本轮日志的三个结论

1. **`[A2F自检]` 定案：网格没问题，jawOpen 能拉开唇缝。**

   下一行索引直接越界。（`GetBlendShapeFrameVertices` 和 `BakeMesh` 都不要求 Read/Write。）

3. **迁移版本号写错**：`LatestConfigVersion` 仍是 1，但有 `configVersion < 2` 分支
   → 日志一直打「升级到 v1」，且**每轮启动都会重跑 <2 分支，用户在 Inspector 里调的值会被反复覆盖**。

## 本轮改动
- `Audio2FaceDiffusionConfig`：`LatestConfigVersion` 1 → **3**；v2 分支 `jawOpenGain` 1.5 → **2.0**
  （自检 jawOpen(1.0)=3.14% 正常，但驱动峰值只有 0.72 → 实际只开 ~2.3%；提到 2.0 让峰值顶到
  ~0.95，接近手动扫掠效果，上限由 clamp 1.0 兜住）
- **探针 v4：不推算，直接量。** 每个 pose 打满烘一次 BakeMesh，系数 = 「该 pose 打满时的上下唇
  质心距离」−「静息距离」。BakeMesh 不要求 Read/Write、不依赖网格轴向；Unity blendshape 本身
  线性叠加，所以 Σ w_i·coeff_i 是精确解。52 次烘只在 Start 做一次（几十 ms）。
- **新增 `[A2F实测]`**：播放中每 30 帧烘一次网格量真实唇缝，每 8 次采样（≈4s）汇总一条
  `[A2F实测] 唇缝真实开度 = [min% .. max%] 网格高（静息基准=X%）| jawOpen 峰值=… (Strength=…)`。
  **这是终局证据**：上限≈静息 → 权重没落到网格（查 Strength/绑定）；上限明显 > 静息 → 确实张开了。
- 修 `_apJawW` 从未赋值（一直是 0）；探针日志补静息唇缝与实测耗时。

# 2026-09-22（第十三轮）根因定案：Tester 姿序错位（Awake 早于 Start）→ 实时驱动权重全写串

## 诊断（两条心跳对账 = 指纹）
同一帧数组、同一网格：
- `[A2F写入] jawOpen 峰值=1.00`（Component._iJawOpenCoeff = SkinSolver.PoseNames 里的 jawOpen）
- `[A2F驱动] jawOpen 峰值=0.11`（Tester.IndexOf("jawOpen") on _poses）
→ 两边对 frame 的下标解释不同 = pose 序错位。`[A2F实测] 唇缝 1.38%~3.60%`（静息 1.19%）→ 嘴几乎没开。
「上唇往下、下唇也往下」= 权重写串后 mouthLowerDown/mouthPress 等落到错误唇形上。

## 根因（已定案）
`Audio2FaceBlendshapeTester.BuildMap()` 在 **Awake** 里读 `Driver.PoseNames`，
但 `Audio2FaceDiffusionComponent._pipeline` 到 **Start** 才 new（Unity 所有 Awake 先于所有 Start）
→ Awake 时 PoseNames 恒 null → `_poses` 退化成 `ArkItBlendshapeNames.All52`（**字母序**），
而 frame[0..51] 是 `SkinSolver.PoseNames`（**NVIDIA 自定义序**）。
`OnDriverFrame`（ApplyFrame 之后经 OnFrameApplied 触发 = **最终写入者**）把 frame[i] 写给
All52[i] 对应的 blendshape → 每个权重落错形状。
手动扫掠为什么正常：_w/_map/IndexOf 全在 All52 一套序里自洽，只写一个权重，不串。
（DriveGain 场景序列化值=1，已排除增益问题。）

## 修复（Audio2FaceBlendshapeTester.cs）
- 新增 `ResolvePoseNames()` + `EnsureMap()`：pose 源一变就重建 _poses/_map，
  实时驱动强制用 `Driver.PoseNames`（与 frame 同序）；All52 只做无 Driver 兜底。
  Awake/Update/ApplyManual/OnDriverFrame/SetPose/StartSweep/ZeroAll/PlayClipAndDrive 全过 EnsureMap。
- `BuildMap(poseNames)` 打印 pose 序来源；兜底时告警。
- `[A2F驱动]` 启动日志加 `pose序=… | jawOpen@idx=N→网格#M`；心跳加 DriveGain、补 `_driveJawPeak` 窗口重置（原来从不重置，「本秒峰值」名不副实）。
- Component 心跳注释加对账指引（写入≈1 / 驱动≈0.x = 姿序又不同步）。

## 下轮判据
- 启动日志：`pose 序=Driver.PoseNames(与 frame 同序)`，`jawOpen@idx=N` 两边一致
- `[A2F写入]` 与 `[A2F驱动]` 的 jawOpen 峰值应一致（≈0.9~1.0）
- `[A2F实测]` 唇缝上限应到 3~5%（静息 1.19% 的 2.5 倍以上），嘴巴肉眼可见张开

# 2026-09-22（第十四轮）推理后端诊断：配置 CUDA 实际跑在 CPU（包冲突）→ 修复 + 计时对账

## 触发
用户：「当前使用的是gpu推理还是cpu推理，优化一下推理速度」

## 结论：一直是 CPU 推理（尽管场景 executionProvider=CUDA）
根因是 **Windows DLL 基名冲突**：
- `onnxruntime`（managed C#）、`onnxruntime-cpu`（Plugins/Win/onnxruntime.dll 14.1MB CPU 构建）、
  `onnxruntime-cuda`（同名 onnxruntime.dll 13.3MB CUDA 构建 + providers_cuda.dll 322MB + providers_tensorrt.dll）
  三个 UPM 包同时装着，两个 native 包都带 `Plugins/Win/onnxruntime.dll`。
- Windows 按基名只加载先注册的那个（字母序 onnxruntime-cpu 在前）→ 加载的是 **CPU 构建** →
  OrtApi 里没有 `OrtSessionOptionsAppendExecutionProvider_CUDA` →
  `MakeSessionOptionWithCudaProvider` 抛异常 → 旧代码只 `Debug.LogWarning(ex.Message)` 就**静默回退 CPU**。
- 机器本身没问题：GTX 1070 8GB、驱动 572.60、CUDA toolkit 12.8 已装。
- TensorRT 路线本机不可用（没装 TensorRT runtime / nvinfer），且 GTX 1070 是 Pascal——就算装了也要禁 FP16。

## 本轮改动
1. `Packages/manifest.json`：**移除 `onnxruntime-cpu`**（依赖方向核实过：没人依赖它，它依赖 onnxruntime），
   只留 managed + cuda。Unity 会自动重新 resolve。
2. `Audio2FaceDiffusionModel.cs`：
   - 新增 `public string ActiveProvider`（TensorRT/CUDA/CPU/未初始化），`CreateSessionOptions` 改实例方法并在各分支赋值。
   - 回退日志 `Debug.LogWarning(ex.Message)` → **`Debug.LogError` + 全量 `{ex}`**（DLL 加载失败原因在 ToString 里）。
   - 配置本来就选 CPU 与「回退到 CPU」分开表述。
   - Initialize 尾部加 **`★ 推理后端=…`** 一眼对账日志（CPU 时附带排查提示）。
3. `Audio2FaceDiffusionPipeline.cs`：`WorkerLoop` 加 **`[A2F推理] #N 单次=XXms 后端=…`**（前 3 次每次打，
   之后每 20 次一条）。单次耗时是推理快慢的唯一判据。

## 下轮判据（用户重跑看这三处）
- 启动日志 `★ 推理后端=CUDA`（若仍是 CPU，LogError 里有完整异常，多半是 providers_cuda.dll 没加载/被杀软拦）
- `[A2F推理]` 单次耗时：CUDA 预期**几十 ms**（第 1 次含 cudnn autotune 偏慢正常）；CPU 是几百 ms~秒级（离线实测 ~0.5s/次）
- manifest 改动后 Unity 需重新 resolve 包（进编辑器等编译完）
